# Plan 013 — Admin Dashboard: Appointments management (confirm/cancel)

- Status: active
- Owner: orchestrator
- Last updated: 2026-08-20
- Scope-Agents: frontend, booking-service, api-gateway, qa, security

## Goal
Implement Screen 7 (Admin Dashboard: Appointments) per the PRD: an authenticated Admin page listing all `Appointment`s, filterable by date and status, with per-appointment confirm (`pending` -> `confirmed`) and cancel (`pending`/`confirmed` -> `cancelled`, releasing the `TimeSlot` back to `open`) actions — F9 (`GET /api/appointments`), F10 (`PATCH /api/appointments/:id/confirm`), F11 (`PATCH /api/appointments/:id/cancel`), all served by `booking-service` via `api-gateway` behind `verifyJwt`, mirroring the `service-proxy` pattern plan 012 established.

## Scope
- In scope (`backend/booking-service/api/appointment/`): `listAppointments(filter: { date?: string; status?: AppointmentStatus })` in `appointment.service.ts` (admin-only, no `deletedAt`/customer-visibility restriction beyond the model's existing soft-delete hook, joined with `serviceId`/`timeSlotId` for display fields), `confirmAppointment(id)` (atomic `pending` -> `confirmed` conditional update), `cancelAppointment(id)` (atomic `pending`/`confirmed` -> `cancelled` conditional update that ALSO releases the linked `TimeSlot` back to `open`, undoing whatever hold/booked state it was in); corresponding controller handlers in `appointment.controller.ts`; new routes `GET /api/appointments`, `PATCH /api/appointments/:id/confirm`, `PATCH /api/appointments/:id/cancel` added to `appointment.routes.ts`. No auth check in `booking-service` itself — same trust boundary as plan 012 (gateway-verified only).
- In scope (`backend/booking-service/api/time-slot/`): `releaseTimeSlot(timeSlotId)` or an equivalent exported helper in `time-slot.service.ts` that `cancelAppointment` calls to set the slot's `status` back to `open` (and clear `heldAt` if present) — this is new write behavior on `TimeSlot` triggered from the `appointment` module, so it must live behind a single exported function rather than `appointment.service.ts` reaching into `TimeSlot` with an ad hoc update, to keep `seat-concurrency-layer`'s single-source-of-truth rule intact.
- In scope (`backend/api-gateway/api/`): an `appointment-proxy` module (route + controller + service, mirroring `service-proxy` exactly) forwarding `GET /api/appointments`, `PATCH /api/appointments/:id/confirm`, `PATCH /api/appointments/:id/cancel` to `booking-service`; mounted in `app.ts` as `app.use('/api/appointments', verifyJwt, appointmentProxyRouter)` — this is precisely the "NOTE" `app.ts` already left for this task (see plan 012's `app.ts`, line noting F9-F11 "land with Screen 7").
- In scope (`frontend/src/`): `services/appointments.service.ts` — `getAppointments(filter)`, `confirmAppointment(id)`, `cancelAppointment(id)`, all via `api-gateway` through the shared `http.service.ts` client (JWT attached automatically, per plan 011); an `AdminAppointmentsPage` (list/table view — see Open Questions on calendar vs. list — of all appointments with service name, date/time, customer name/phone, status shown via label + icon per `accessibility-layer`), date and status filter controls, and per-row "Confirm"/"Cancel" actions (each gated to the appropriate current status, with a confirmation step before cancel since it is a customer-facing, notification-worthy action); wiring `/admin/appointments` as a new route behind `ProtectedRoute`, and adding it to whatever Admin nav shell plan 012 left (or a minimal nav link if none exists yet).
- Out of scope: notifying the customer of confirm/cancel (PRD does not require it for F10/F11, unlike F4b for booking; no `notification-service` change), re-opening a cancelled appointment (PRD only specifies confirm/cancel, no "un-cancel"), any change to the Customer-facing booking flow (Screens 1-4) or the existing `POST /api/appointments` / `GET /api/appointments/:id` routes, calendar-grid UI (deferred per Open Questions to a simple filterable list for v1).
- Repo-relative scope: frontend changes under `frontend/src/`; backend changes under `backend/booking-service/api/appointment/` and `backend/booking-service/api/time-slot/`; gateway changes under `backend/api-gateway/api/` (new `appointment-proxy/` module + `app.ts` wiring). No changes to `backend/user-service/` or `backend/notification-service/`.

## Assumptions
- The `verifyJwt` middleware, `ProtectedRoute`, auth store, and the gateway-proxy pattern (plans 011-012) are directly reusable unchanged; this task only adds a third resource's proxy module.
- `TimeSlot` and `Appointment` models (plans 004/009) already have the fields this task needs (`TimeSlot.status`, `Appointment.status`); no schema migration required.
- An Admin nav shell/landing page may or may not already exist from plan 012 — if plan 012 only wired `/admin/services` directly, this task adds `/admin/appointments` as a sibling route and, if cheap, a minimal shared nav; building a full Admin shell is not blocking and not the focus of this task.
- "Releasing the TimeSlot back to open" applies regardless of whether the slot is currently `held` or `booked` at cancel time — in practice a cancel only ever targets a `booked` slot (an appointment implies its slot was successfully booked per `createAppointment`), but the release logic is written against slot state generically rather than assuming `booked`, since that is the safer/more general precondition.

## Open Questions
1. Should Screen 7 be a true calendar view or a filterable list/table for v1?
   - Recommended: a filterable list/table (date picker + status filter), not a calendar grid — the PRD says "Calendar or list view," a single-groomer clinic's volume doesn't need a calendar's visual density, and a list is far cheaper to make accessible (no custom grid semantics) and keyboard-navigable.
2. Should `cancelAppointment` be allowed from `pending` AND `confirmed` (per PRD F11 wording), or only from `confirmed`?
   - Recommended: allow both `pending -> cancelled` and `confirmed -> cancelled`, exactly as F11 states ("cancel (`confirmed`/`pending` -> `cancelled`)") — a pending appointment the admin simply doesn't want to honor must still be cancellable without first confirming it.
3. Should cancelling an appointment whose `TimeSlot` was never successfully released (e.g. already reassigned somehow) fail loudly or degrade gracefully?
   - Recommended: the `Appointment` status transition and the `TimeSlot` release should be a single atomic-as-possible operation ordered so the Appointment only flips to `cancelled` if the slot release also succeeds (or is verified idempotent-safe to retry) — if the slot is missing/already `open`, treat that as a no-op success rather than blocking the cancel, since the Appointment's own status is the more important source of truth for the Admin's action; flagged for `security`/data-integrity review given it is the first path that mutates two collections from one Admin action.
4. Should the confirm/cancel actions require a second confirmation step in the UI (e.g. "Are you sure you want to cancel?")?
   - Recommended: yes for cancel only (it is destructive to the customer's booking and releases their slot to the public), no extra confirmation for confirm (a low-risk, reversible-by-cancel action) — consistent with plan 012's precedent of confirming only the more consequential action.
5. Should the Admin routes live under a new `/api/appointments` gateway mount distinct from the public `POST /api/appointments` / `GET /api/appointments/:id` routes the frontend already calls directly against `booking-service`?
   - Recommended: yes, mount `GET /api/appointments` (list) and the two `PATCH` routes behind `verifyJwt` at the gateway under the same `/api/appointments` path prefix (this does not collide with the public routes since the public flow calls `booking-service` directly, never through the gateway, exactly as plan 012 established for `/api/services`).

## Steps
1. `backend/booking-service/api/time-slot/time-slot.service.ts` — add `releaseTimeSlot(timeSlotUuid: string)`: atomic `findOneAndUpdate` on `TimeSlot` (matched by `uuid`) setting `status: 'open'` and clearing `heldAt`/hold-related fields if present; treats "already open" or "not found" as a safe no-op return, not an error (Open Question 3).
2. `backend/booking-service/api/appointment/appointment.service.ts` — add `listAppointments(filter)`: builds a Mongo filter from optional `date` (matches the joined `TimeSlot.date`) and `status`, populates `serviceId`/`timeSlotId` for display (name, date/time), returns an admin projection (may include more than `PublicAppointment` — customer contact fields are already visible to the Admin by design). Add `confirmAppointment(id)`: atomic `findOneAndUpdate` on `Appointment` (`uuid: id, status: 'pending'`) -> `status: 'confirmed'`; returns a discriminated result (`confirmed | not-found | conflict`) mirroring `CreateAppointmentResult`'s style. Add `cancelAppointment(id)`: atomic `findOneAndUpdate` on `Appointment` (`uuid: id, status: { $in: ['pending', 'confirmed'] }`) -> `status: 'cancelled'`, then calls `releaseTimeSlot(appointment.timeSlotId's uuid)`; returns `cancelled | not-found | conflict`.
3. `backend/booking-service/api/appointment/appointment.controller.ts` — add `getAppointments` (parses `date`/`status` query params, validates `status` against `APPOINTMENT_STATUSES` if present, calls `listAppointments`), `patchConfirmAppointment`, `patchCancelAppointment` (call the corresponding service functions, map `not-found` -> 404, `conflict` -> 409, success -> 200 with the updated Appointment), following `postAppointment`'s existing error-envelope style.
4. `backend/booking-service/api/appointment/appointment.routes.ts` — add `GET /`, `PATCH /:id/confirm`, `PATCH /:id/cancel` to `appointmentRouter`.
5. `backend/api-gateway/api/appointment-proxy/appointment-proxy.service.ts`, `appointment-proxy.controller.ts`, `appointment-proxy.routes.ts` — new module mirroring `service-proxy`'s shape exactly: forwards `GET /`, `PATCH /:id/confirm`, `PATCH /:id/cancel` to `booking-service`, relaying status/body and query params.
6. `backend/api-gateway/api/app.ts` — replace the existing "NOTE: the Admin Appointment routes... land with Screen 7" comment with `app.use('/api/appointments', verifyJwt, appointmentProxyRouter)`; confirm this does not collide with the public `POST /api/appointments` / `GET /api/appointments/:id` routes (unaffected — frontend calls `booking-service` directly for those, no gateway route for them exists or is added here).
7. `frontend/src/services/appointments.service.ts` — add `getAppointments(filter?: { date?: string; status?: AppointmentStatus })`, `confirmAppointment(id)`, `cancelAppointment(id)`, all calling `api-gateway`'s admin routes via the shared `http.service.ts` client.
8. `frontend/src/pages/AdminAppointmentsPage.tsx` — page component: date and status filter controls, fetches `getAppointments(filter)` on mount/filter-change, renders a table/list (service name, date/time, customer name/phone, status via label + icon per `accessibility-layer`), per-row "Confirm" action (visible only when `status === 'pending'`) and "Cancel" action (visible when `status` is `pending` or `confirmed`, with a confirmation step per Open Question 4).
9. `frontend/src/App.tsx` — add `/admin/appointments` route wrapped in `ProtectedRoute`, rendering `AdminAppointmentsPage`; link it from wherever `/admin/services` is reachable (plan 012's Admin nav/placeholder).
10. Manual verification: log in as Admin, view the Appointments list including a pending, a confirmed, and a cancelled seed appointment; filter by date and by status and confirm the list narrows correctly; confirm a pending appointment and see its status flip; cancel a confirmed appointment and confirm its linked `TimeSlot` becomes bookable again on the public Screen 2 for that service/date.

## Validation
- `GET /api/appointments` (via `api-gateway`, valid Admin JWT) returns all appointments with service/time-slot display fields; supports `?date=` and `?status=` filters narrowing the result set; without a token or with an invalid/expired token returns `401`.
- `PATCH /api/appointments/:id/confirm` transitions a `pending` appointment to `confirmed` and returns the updated record; called on an already-`confirmed` or `cancelled` appointment returns `409`; unknown `:id` returns `404`.
- `PATCH /api/appointments/:id/cancel` transitions a `pending` or `confirmed` appointment to `cancelled`, and the linked `TimeSlot` becomes `status: 'open'` immediately after (verified by re-querying `GET /api/time-slots?serviceId=&date=` and seeing the freed slot); called on an already-`cancelled` appointment returns `409`; unknown `:id` returns `404`.
- Both `PATCH` routes and the `GET` route reject requests without a valid `Authorization: Bearer <token>` with `401`, proving they are gated by `verifyJwt`.
- Concurrency check: two near-simultaneous cancel requests against the same appointment result in exactly one `cancelled` transition and one `409`/no-op for the second — no double release of the same `TimeSlot`.
- Frontend: `AdminAppointmentsPage` lists appointments with an accessible, non-color-only status indicator; date/status filters narrow the visible list; Confirm and Cancel actions update the row's status immediately after a successful call; Cancel prompts a confirmation step before submitting.
- Keyboard-only navigation can reach and activate every filter control and every Confirm/Cancel action.
- No changes leak into `backend/user-service/` or `backend/notification-service/`; the existing public `POST /api/appointments` and `GET /api/appointments/:id` behavior is unchanged.

## Risks
- **Two-collection write from one Admin action**: `cancelAppointment` must update both `Appointment.status` and `TimeSlot.status` consistently — a partial failure (Appointment cancelled but slot never released, or vice versa) would either strand a customer's slot as permanently unbookable or double-free a slot. Mitigated by ordering the writes so the Appointment transition is the atomic precondition and slot release is treated as idempotent/best-effort-but-verified (Open Question 3); `security` is included in Scope-Agents to review this specific two-write path, since it's the first Admin action in the app that mutates a collection (`TimeSlot`) other than the one its own route names.
- **Concurrent confirm/cancel double-submits**: without atomic conditional updates (matching on current `status` in the filter, per `createAppointment`'s existing pattern), a double-click or two admin sessions could race. Mitigated by using the same single-atomic-`findOneAndUpdate`-with-status-precondition pattern `createAppointment`/`holdTimeSlot` already established (`seat-concurrency-layer`); `booking-service` is included in Scope-Agents because this task adds the new atomic transitions themselves, not just consumes existing ones.
- **New gateway-proxied admin resource**: `api-gateway` is included in Scope-Agents because this task adds real proxy code (`appointment-proxy/`) and a new `verifyJwt`-gated mount, following but not identical to plan 012's `service-proxy` — worth independent review that the mount doesn't shadow or interfere with any future public `/api/appointments` gateway route.
- **PII exposure surface**: the Admin list response includes customer name/phone/email, same as the existing receipt endpoint, but now aggregated across all appointments in one response — `security` review should confirm the `verifyJwt` gate is airtight on this new `GET /api/appointments` route (no accidental unauthenticated path) and that filtering/pagination doesn't leak beyond the Admin's own JWT scope (there is only one Admin account in v1, but the check should still be verified explicitly, not assumed).
- No `user-service` or `notification-service` code is touched (confirm/cancel do not trigger notifications per PRD), so they remain correctly excluded from Scope-Agents.
