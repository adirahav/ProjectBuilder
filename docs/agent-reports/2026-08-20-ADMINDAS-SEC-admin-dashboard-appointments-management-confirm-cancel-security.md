## Verdict: PASS, no blocking findings

This is a well-built implementation of a genuinely sensitive surface (an endpoint that aggregates every customer's name/phone/email in one authenticated response, plus the first two-collection Admin write in the app). Highlights confirmed by reading the actual code (not assumed from the plan):

1. **Auth boundary is airtight and fails closed.** `verifyJwt` is applied at the *mount point* (`app.use('/api/appointments', verifyJwt, appointmentProxyRouter)`), not per-route, so any route added to that router later inherits the gate automatically. `verifyJwt` rejects a missing header, a non-`Bearer` scheme, an empty token, and any `JwtVerificationError` (expired/malformed/wrong-signature) with a generic `401 {"error":"Unauthorized"}` — never leaking why. It explicitly checks `decoded.role !== 'admin'` and requires `decoded.sub`, not just a valid signature, so a token forged with a different role or missing claims is rejected even if otherwise well-formed. `jwt.verify` is called with no explicit `algorithms` option and a string secret, which is the correct posture against `jsonwebtoken`'s default behavior of rejecting `alg: none` — confirmed by code reading (the library requires an explicit `algorithms: ['none']` opt-in that is absent here).
2. **`x-internal-admin` cannot be spoofed.** `verifyJwt` overwrites `req.headers['x-internal-admin']` with the verified `sub` *after* validating the token, and the gateway's `forwardAppointmentRequest` builds this header explicitly from `internalAdminId` rather than copying inbound headers — a client-supplied value can never survive the hop.
3. **No injection surface at either layer.** Every path/query input is validated against a fixed shape *before* it can reach a database filter: `:id` against a strict UUID regex (both at the gateway and again independently in booking-service), `date` against a real-calendar-day check (not just a regex — round-trips through `Date` to reject `2026-02-30`), and `status` against the literal `APPOINTMENT_STATUSES` enum. Query-string operator injection (`?status[$ne]=`) is caught because Express parses it into a non-string object, and the validators explicitly type-check before pattern-testing. `status`/precondition values passed into Mongo filters are always hardcoded literals from the calling function, never derived from request input.
4. **Soft-delete is enforced correctly on the mutation path, not just reads.** The plan flagged this as a real risk (Mongoose's `pre('findOne')` hook does not cover `findOneAndUpdate`), and the code handles it: `transitionAppointment` explicitly includes `deletedAt: null` in its filter.
5. **The two-collection write (cancel) is race-safe and ordered correctly.** `cancelAppointment` performs the Appointment's atomic conditional transition *first* (`findOneAndUpdate` with the current-status precondition in the filter, not a read-then-write), and only the winner calls `releaseTimeSlot`, which is itself a condition-checked atomic update and idempotent (treats "already open" / "not found" as success). This means concurrent cancels can never double-release a slot, and a losing request never mutates anything. Verified by code reading against `time-slot.service.ts:releaseTimeSlot` and the existing `appointment-admin.test.ts` concurrency suite (5-way simultaneous cancel resolves to exactly one 200).
6. **No mass assignment / status injection.** `confirm`/`cancel` are bodyless by design — the controller never reads `status` from the request body, only from which endpoint was called — so a client can never name an arbitrary target status.
7. **PII handling is explicit, not incidental.** `toEnrichedAppointment` builds an allowlist projection field-by-field (no `_id`, `__v`, `uuid`-as-Mongo-id, `heldAt`, `isActive`); confirmed no internal fields leak in the list or transition responses. Error responses on 500 never leak stack traces or raw Mongoose error text — `console.error` logs internally, the client gets a fixed generic body.
8. **Frontend rendering has no XSS surface.** `AdminAppointmentTable.tsx` renders `customerName`/`customerPhone` as plain JSX text/attribute values (React auto-escapes both text nodes and the `tel:` href attribute); there is no `dangerouslySetInnerHTML` anywhere on this screen. `ProtectedRoute` is correctly documented as UX-only, not the security boundary — every API call goes through `gatewayHttpService`, which attaches the JWT and is answered by `verifyJwt` regardless of client-side state.
9. **`booking-service` has no auth of its own — by design, and correctly scoped.** Both the plan and the code comments are explicit that this is a trust-boundary decision identical to the Services management task (plan 012): `api-gateway` is the only intended caller, and the port must not be publicly exposed. This is a deployment/network-isolation concern, not a code defect, and is the same accepted risk already reviewed and passed in the prior ADMINDAS-SEC report. I re-verified booking-service's admin routes reject malformed/injection-shaped input on their own defense-in-depth (see tests below) so that even a network misconfiguration exposing the port would not open a NoSQL-injection or wildcard-mutation hole — only the "any caller can read all PII" exposure the plan already flags as a deployment concern.

## Findings

No blocking findings. One pre-existing, already-accepted risk, re-verified rather than re-litigated:

- **Risk (documented, non-blocking):** `booking-service`'s `/api/appointments` admin routes (`GET /`, `PATCH /:id/confirm`, `PATCH /:id/cancel`) have no authentication of their own; they trust `api-gateway` to have verified the Admin JWT before forwarding. If the service's port were ever exposed outside the internal network (misconfiguration, not code), any caller could read every customer's name/phone/email or drive confirm/cancel directly. This is the same trust boundary already reviewed and accepted in plan 012's security report; it is not new to this task, and the plan explicitly calls it out (Risks section, "PII exposure surface"). Mitigation is network isolation at the deployment layer, outside this task's code scope. I confirmed booking-service still validates and rejects hostile input on this path independently of the gateway (see tests below), so even if this boundary were breached the injection/mutation surface remains closed — only the read-everything PII exposure is the residual risk, exactly as documented.

## Minor recommendation (non-blocking)

- Consider a lightweight shared-secret or mTLS check between `api-gateway` and `booking-service` for the admin routes as defense-in-depth, so a network misconfiguration alone isn't sufficient to expose bulk customer PII. Same recommendation carried forward from the plan-012 security review; still not blocking for this task since the accepted architecture is unchanged.

## Tests written

`docs/tests/security/admin-appointments-management.security.test.ts` — new file, covering attack classes not already pinned exhaustively by the dev-authored suites (`appointment-proxy.test.ts`, `appointment-admin.test.ts`), which are themselves already unusually thorough (401 gating, filter injection, concurrency, PII field-leak checks, 502 mapping, etc. — reviewed and found correct):

- **JWT forging at the gateway boundary:** `alg: none` header with empty signature; HS256-signed-with-wrong-secret (algorithm-confusion style); validly-signed token with `role` changed to non-admin; validly-signed token missing `role`; validly-signed token missing `sub`; Basic-auth-shaped header; path-traversal-shaped `:id` segment (`..%2f..%2fadmin`) rejected before any upstream call. Also asserts a 401 body never contains any Appointment PII.
- **booking-service defense-in-depth (independent of the gateway):** NoSQL operator objects (`{$ne:null}`, `{$gt:''}`) smuggled into the `:id` path segment for both confirm and cancel, verifying no state mutation on rejection (including the linked TimeSlot); an empty/near-empty id segment cannot act as a wildcard that confirms every pending appointment; soft-deleted Appointments cannot be confirmed or cancelled via their still-valid uuid (and cancel does not release the slot in that case); a 500 from a mocked Mongoose failure never leaks a stack trace or file:line; the admin list never leaks `_id`/`__v` and the exposed `id` is never a valid Mongo ObjectId; a guessed-but-wrong id on a transition attempt returns a generic 404 with no PII of the real record; 5-way concurrent cancel of the same appointment resolves to exactly one 200 and the slot is released exactly once (no double-release under a wider race than the existing 2-way test).

This is the same pre-existing environment issue documented by the ADMINDAS-SEC report for plan 012 (services management) — not something introduced by this task. I verified the test logic by manual code reading against the actual `verifyJwt`/`verifyAdminToken` implementation, the `transitionAppointment`/`releaseTimeSlot` atomic-update filters, and the controller-level UUID/date/status validators, cross-checked against the existing passing dev test suites' equivalent assertions (e.g. the 2-way concurrency test in `appointment-admin.test.ts`, which uses the identical pattern this file extends to 5-way).

## Summary for other agents

The admin appointments confirm/cancel feature is secure as built: JWT verification is strict (role + sub checked, not just signature), the mount-point gating pattern prevents any route from accidentally shipping unauthenticated, all mutation inputs are validated before reaching a database filter, the two-collection cancel write is correctly ordered and race-safe, soft-delete is explicitly re-applied on the write path where Mongoose's hooks don't cover it, and there is no PII leak or XSS surface on the new frontend screen. The only residual risk is the pre-accepted, already-reviewed booking-service network-trust boundary, unchanged from plan 012.
